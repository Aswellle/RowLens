# RowLens 决策记录（ADR）

按时间顺序登记。修改既有决策时新增条目，不删除旧条目。

## ADR-001：React + TypeScript strict + Vite，不使用大型 UI 组件库

来源：`docs/02-architecture.md`。理由：UI 状态与可访问性交互易于组织，
构建产物为纯静态文件，无服务端。样式使用原生 CSS + CSS variables。

## ADR-002：IndexedDB 作为行级临时存储

来源：`docs/02-architecture.md`。数据库名 `rowlens-local`，版本 1；store：
`datasets`（keyPath `id`）、`rows`（compound key `[datasetId, rowIndex]`）、
`importErrors`。React state 永远不持有全量行数据。接受浏览器配额差异，
配额错误必须以 `STORAGE_QUOTA_EXCEEDED` 单独处理并触发清理。

## ADR-003：Papa Parse 仅用于 CSV/TSV；JSONL 自建有界行流 parser

来源：`docs/02-architecture.md`。JSONL 使用 `File.stream()` +
`TextDecoder`（`{ stream: true }`）分块解码，缓冲区只保留未完成的当前行，
最大行长 5 MiB（`MAX_JSONL_LINE_BYTES`，待实测调整）。

## ADR-004：列值一律字符串，不做隐式类型转换

来源：PRD FR-02 与数据契约 §4。`00123` 保持 `00123`，日期文本原样保留。
排序为稳定 UTF-16 字符串排序；缺失值两种方向都排最后。

## ADR-005：源文件只读；清洗规则为可序列化管线配置

来源：PRD FR-05。清洗步骤只有 `id`/类型/参数/enabled/名称；结果通过重算
派生，导出只写新文件（默认 `-cleaned` 后缀）。

`^22.12.0 || ^24.0.0 || >=26.0.0`。`package.json` engines 定

## ADR-009：`test:unit` 脚本直接为 `vitest run`

（2026-10-25，Phase 0）测试文档 §5 曾写 `npm run test:unit -- --run`（假设
watch 脚本 + 附加参数）。为避免 CI 参数歧义，脚本本身定义为一次性运行，
`test:watch` 才是交互模式。

## ADR-010：Phase 0 的"契约测试"范围 = 类型契约 + 类型级断言 + 纯函数单测

（2026-10-25，Phase 0）路线图要求"定义解析/导出契约测试"，但解析器与导出
器在 Phase 2/5 才实现。Phase 0 落地为：数据模型与 Worker 消息的
discriminated union 定义（`src/features/**`），配结构锁定单测（消息判别
字段、终态消息集合、错误码目录、列 schema 派生纯函数）。解析器行为夹具
（quoted-newlines、BOM、UTF-8 chunk 边界等）属 Phase 2/5 的测试范围。

## ADR-011：Vite 构建前先跑 `tsc --noEmit`

（2026-10-25，Phase 0）Vite 只转译不做完整类型检查（见技术参考文档），
因此 `build` 脚本为 `tsc --noEmit && vite build`，`typecheck` 单独可跑。
tsconfig 在 strict 基础上追加 `noUncheckedIndexedAccess`、
`exactOptionalPropertyTypes`、`noUncheckedSideEffectImports`、
`noImplicitOverride`。

## ADR-012：导入管线 = 流式分块（内存）+ Worker（主线程）+ 批次 ACK 背压（三者缺一不可）

（2026-10-25，Phase 1 设计时锁定，Phase 2 实现）Papa Parse 的 chunk/step
流式解析与 Web Worker 解决的是不同问题：分块限制瞬时内存峰值（不必把整份
文件读成字符串），Worker 减少主线程阻塞（解析不冻结 UI）。仅靠其中任何一个
都不满足 PRD FR-01 与架构 §7。Phase 2 实现必须同时满足：

1. Worker 内以 chunk 模式驱动 Papa Parse（CSV/TSV）与自建 line streaming
   （JSONL），单批上限 `ROW_WRITE_BATCH_SIZE = 500` 行；
2. Worker 发出 `BATCH` 后暂停解析，等待主线程 IndexedDB 持久化成功并回
   `ACK(batchSeq)` 才继续——生产者快于存储时不形成无界消息队列；
3. 取消幂等，过期 `jobId` 的消息一律忽略（`ImportTerminalMessage` 后到达
   的同 job 消息不得覆盖新状态）。

## ADR-013：TanStack Virtual 只负责渲染虚拟化；查询与内存边界由架构承担

（2026-10-25，Phase 1）`@tanstack/react-virtual` 3.14.22 接入。它是 headless
渲染虚拟化，不会自动解决查询算法或内存问题：搜索/筛选/排序仍按契约
（literal 匹配、稳定排序、缺失值末位）先算出可见 `rowIndex` 列表，组件只
接收该列表和有界 `valueAt` 读取器；全量数据永不进入 React state。

Phase 1 已用两级测试固化该边界：组件测试断言 DOM 行数与数据量无关
（5000 行数据 < 60 个 row 节点）；E2E 在真实 Edge 上复验，并曾当场抓到
workspace grid 隐式 `auto` 行高导致容器被内容撑开、5001 行全部渲染的真实
布局 bug——证明"DOM 行数与 viewport 相关而非总记录数"必须用测试断言，
不能凭感觉认为虚拟化自动生效。

## ADR-014：导入期间的主线程写穿缓存

（2026-10-26）Worker 的每个 BATCH 本就要路过主线程写入 IndexedDB；`InMemoryDataset`
把同一批数据追加进一个模块级、列序紧凑的镜像（React state 之外），网格通过
`getCell(rowIndex, columnIndex)` 同步读取。内存上界受 `MAX_FILE_BYTES`（100 MiB）
约束；当查询 worker（后续步骤）就位后，网格读取将改为游标窗口读取，缓存随之
退役。此为过渡设计，不宣称适用无上限文件。

## ADR-015：Papa Parse 5.7.0 安装与 chunk 模式行为差异

（2026-10-26）papaparse 5.7.0 作为生产依赖安装（ADR-008 补记）。实现时发现并
处理了两个 chunk 模式的实际行为：(1) 文件以换行结尾时 chunk 模式会产出一个
`[""]` 幻影空记录（非 chunk 模式不会）——session 扣留末尾空记录并在完成时按
文件末字节判定真伪；(2) `parser.abort()` 后不保证回调 complete——session 在
abort 时主动进入终态。两者均有测试锁定。

## ADR-016：查询在 worker 中按窗口扫描执行；无 Worker 环境降级到同引擎主线程

（2026-10-26）查询协议每条消息带 `queryId`；query worker 用共享 repository 的
`getAll` 窗口读取（而非保持游标跨 await——挂起的游标会让事务自动提交）喂数据
给与降级路径完全相同的引擎。客户端新查询自动取代旧查询（对旧 id 发 CANCEL、
旧结果按 superseded 结算、晚到消息按 queryId 忽略）。匹配索引受
`QUERY_MATCH_LIMIT`（200k）约束，超限显式提示、绝不静默截断。无模块 Worker 的
环境走 `runLocalQuery`（同窗口读取 + 快路径：无谓词无排序时直接用 finalize 的
行数生成全量索引）。样本数据集也写入 IndexedDB 走同一条查询路径。

## ADR-017：deleteDataset 按 finalize 行数直删；事务内禁止 await

（2026-10-26）实测发现两处违反 IndexedDB 事务规则/性能雷区并修复：(1) 在事务
回调之间 `await` 会让事务自动提交，后续请求落在死事务上——删除改为单事务内
同步发起全部请求；(2) 索引游标逐键删除在 fake-indexeddb 下是平方级（5000 行
41 秒）。由于行的复合键是 `[datasetId, rowIndex]` 且 `ready` 数据集的 rowCount
精确描述键范围，改为直接按键删除；未 finalize 的数据集仍走游标兜底。

## ADR-018：清洗 = 可序列化配置的单趟行变换，嵌入查询管线执行

（2026-10-26）清洗步骤是纯数据（trim / remove-empty-rows / remove-duplicates /
select-columns，含 enabled 与作用范围），经 JSON 往返可复现相同结果。执行上不做
独立的"清洗 worker"：查询引擎增加可选 transform 钩子，在搜索/筛选命中之后、排序
键采集之前应用（排序与幸存索引反映清洗后的值），worker 与本地降级在**同一趟数
据扫描**内完成查询+清洗并返回逐步影响摘要——避免对数据集的第二次全量扫描。
"全部列"作用域解析为管线该位置的有效列（select-columns 会收窄后续步骤）；
去重键为 JSON 编码的精确值元组（首见保留、无哈希碰撞风险），比较规则 exact/
trimmed 由用户选择。原始 IndexedDB 行永不修改；select-columns 同时收窄网格展示
列（与手动隐藏列正交）。禁用步骤跳过但保留配置；影响计数在后台重算完成前保留
旧值并显示 Recomputing…。

## ADR-019：导出 = 流式序列化 + 保存器抽象；回退下载受独立字节上限

（2026-10-26）导出分三层：纯编码（必要引号、双引号转义、CRLF、OWASP 前缀检测
=, +, -, @, tab, CR 含空白/控制字符遮蔽；safe 模式加 `'` 前缀并计数，raw 不改动
值）、流式序列化器（有界 chunk、行/防护单元格/字节统计）、保存器抽象。保存器
优先 File System Access writable（真流式、无 Object URL；用户关掉选择器视为取消
静默收场），否则回退内存聚合下载——受 `EXPORT_FALLBACK_MAX_BYTES`（150 MiB）独立
上限约束，超限拒绝并给出说明而非尝试分配；Object URL 仅在 close 时创建、延迟
revoke（EXPORT_URL_REVOKE_DELAY_MS）。取消与写错误一律 abort 保存器且绝不声称已
保存。范围语义：filtered = 当前视图行序（含查询排序）；all = 全部记录过清洗管线
（"完整数据的清洗版本"，与产品简报一致）。E2E 以 headless 无保存选择器为由在测试
中移除 showSaveFilePicker 走下载路径并断言下载文件字节内容。另：Papa 的
UndetectableDelimiter 是提示级信息（回退逗号即我们的默认），不再计为 malformed。

## ADR-020：性能基准首测结论与两处即时修正

（2026-10-26）按测试文档 §4 跑 P1/P2/P3 基准（数据与复现见
docs/performance-results.md）。基准过程直接促成两处产品修正：

1. **无谓词全量视图快路径（worker 对齐本地路径）**：250k 行数据集的初始
   视图此前也走全表扫描并被 200,000 匹配上限拦截——上限本意约束"带谓词的
   查询结果"，不该挡住数据集的完整视图。快路径由 finalize 行数直接生成
   索引，同时消除一次无谓扫描。
2. **查询 busy 标记补全**：排序/列筛选/Reset/防抖搜索提交此前不置 busy，
   排序"耗时"被测成表头翻转毫秒级——修正后才得到真实的 P3 排序 5.0s。
   基准脚本因此先于用户发现了一个会误导用户的反馈缺口。

基准同时量化了已知瓶颈：全表字面搜索的逐格大小写折叠（P3 64.7s，排序趟
仅 5.0s 佐证）、写穿缓存内存放大（~6.5×）、导出与导入的近线性扩展。缓解
方案（小写化缓存、搜索列范围限制、内存剖析）登记为后续候选，未实施。

## ADR-022：查询 worker 的小写化值缓存

（2026-10-26）搜索/筛选的逐格 `toLocaleLowerCase` 是 P3 基准的绝对瓶颈
（64.7s；排序趟仅 5.0s 佐证）。worker 现按数据集维护折叠值缓存
（行 → 列 → 小写值），首趟惰性构建、跨查询复用，数据集重导入（rowCount
变化）即失效。引擎通过可选 `foldedAt` 钩子取折叠值，无钩子时退回逐格折叠
——语义单一实现，仅取值路径分叉。实测（P2 专项）：首趟 12.4s 建缓存，
重复搜索 2.6s（4.7×）；代价是每格一份小写副本的内存（与写穿缓存同量级，
仍受 100 MiB 导入上限约束）。同时交付：查询取消按钮（StatusLine busy 时
可取消，引擎批次间生效）、单元格 Copy 按钮（Clipboard API + 非安全上下文
execCommand 回退，hover/键盘可达）、360–1440px 四档视口 E2E。

## ADR-023：网格 roving tabindex 与查询结果归约纯函数

（2026-10-26）网格采用 roving tabindex：任一时刻恰有一个单元格可 Tab 到达，
方向键/Home/End/PageUp/PageDown 在可见窗口内移动焦点并经
`scrollToIndex` 把目标行滚入虚拟窗口，点击单元格同步接管焦点（否则
tabIndex=0 的 grid 容器会吞掉点击焦点）。行表头（记录号）暂不在漫游范围内，
已在 README 记录。

同时把查询结果到视图状态的映射抽成纯函数 `reduceQueryOutcome`：此前
cancelled 分支直接返回原状态，`queryBusy` 永不清除——**取消后 Cancel 按钮
会永久滞留**（真实缺陷，基准与手测均未覆盖，新增回归测试锁定）。归约函数
统一 done/limit/failed/cancelled/superseded 五态规则并保持 superseded 时
引用不变以避免无谓重渲染。

## ADR-024：网格矩形选区、行表头语义与剪贴板格式

（2026-10-26）选区坐标采用**视图位置**（当前可见结果列表的行位置 + 可见数据
列下标），列 `-1` 表示记录表头。这样选区天然与搜索/排序/隐藏列后的视图一致，
无需映射回原始行号；代价是结果集变化后旧矩形不再描述同一批记录，因此
`visibleIndices` 引用变化即收敛为活动单元格。

三条契约写在纯函数层（`src/features/grid/selection.ts`），可脱离 DOM 测试：

1. **端点落在行表头即整行**：`boundsOf` 检测任一端点列 < 0 就横向铺满全部
   可见列。行表头是**选择器而非数据**，复制时永不贡献值（否则会把
   "Record 12" 混进用户数据）。这也让从表头往下拖保持整行，而不是退化成
   单列矩形。
2. **读取时钳制**：`boundsOf` 以当前 `rowCount`/`columnCount` 收紧矩形，
   不信任状态里的旧坐标。缩小的结果集或隐藏列不可能让复制越过可见范围。
3. **TSV + CRLF**：制表符分隔、行分隔用 CRLF（Excel/Sheets 无需导入向导），
   含制表符/换行/引号的字段按 RFC 4180 加引号并双写引号。值取自
   `valueAt`，即用户所见（含清洗 trim 后的显示值），复制不会绕到原值后面。

**上限 100,000 单元格**：超限明确拒绝并提示改用 Export CSV，绝不静默截断
（截断的粘贴结果比报错更难发现）。上限按单元格数而非字节数，便于解释。

**剪贴板两条路径**：键盘 Ctrl/Cmd+C 走同步 `copy` 事件写 `clipboardData`
（无需权限、不受非安全上下文限制），选区工具条按钮走异步 Clipboard API 并
回退 `execCommand`；两者共用同一序列化函数，避免内容分叉。

**拖拽边缘自动滚动**：虚拟化只保留屏内行，若不做自动滚动，拖拽选区永远
无法超出当前窗口。实现为每帧按指针进入边缘区的深度计算 1–16px 的有界步长
（`edgeScrollDelta`，纯函数测试覆盖），滚动后重新取指针下的单元格，使选区
跟随内容而非鼠标坐标。帧循环经 ref 调用最新闭包，否则会一直使用拖拽开始
那一帧的窗口与选区状态。

**已知取舍**：无单元格编辑、无 Ctrl+click 多区间选择（区域选择足以覆盖
"复制一块去别处"的主路径）；选区不参与导出范围（导出仍以筛选视图/全量为准）。

## ADR-025：单元格编辑作为内存覆盖层

（2026-10-26）编辑**不写回**任何持久层：覆盖层是
`Map<rowIndex, Map<columnId, string>>`，网格、查询引擎、清洗管线和导出全部
在读取时叠加它。原始 IndexedDB 行、源文件、以及"源文件只读"的承诺因此都不
需要额外机制来保证——不存在写路径。代价是刷新即丢失，这一点在 README 与
CHANGELOG 明确写出，不假装是持久编辑。

关键设计点：

1. **按 columnId 而不是显示位置索引**：隐藏列、`select-columns` 清洗步骤、
   重新排序都不会把编辑挪到别的列。
2. **两种"空"必须区分**：`undefined` = 无覆盖（回落到存储值），`''` = 用户
   把单元格清空。`EditChange` 的 `before`/`after` 存的是**覆盖层的值**（
   `null` 表示无覆盖），因此连续撤销会沿编辑历史逐步回退，而不是一次跳到
   存储值。`EditInput` 额外带 `displayed` 与 `stored`：用户把原值重新输入
   一遍时覆盖项被移除，不会留下一个"看起来没改但标记为已编辑"的幽灵项。
3. **查询覆盖层先于一切**：引擎在搜索/筛选/排序/清洗之前套用编辑，所以
   编辑后的值能被搜到、能被排序、也能被清洗步骤看到。worker 的折叠值缓存
   （ADR-022）存的是编辑前的值，因此被编辑的单元格绕过缓存直接折叠。
4. **上限 5,000 单元格**：覆盖层随每个查询请求一起 structured clone，无上限
   会让每次按键都变成大对象复制。超限返回明确的拒绝文案，网格关闭编辑器
   并播报原因，不静默丢弃草稿。
5. **撤销栈在视图状态里**：`applyEdits` 返回新状态而非修改，`Reset edits`
   也是一条可撤销的批量动作。撤销/重做是纯函数，测试不需要 DOM。
6. **焦点契约**：编辑器内部的 mousedown 不再冒泡成单元格选择（否则点击输入
   框会把草稿提交并抢走焦点）；焦点初始化只在编辑器**打开**时执行一次，
   否则每敲一个字符都会重置光标与选区。
7. **文档级快捷键**：Ctrl/Cmd+Z 绑定在 window 上，但在 input/textarea 内让位
   给浏览器原生撤销，避免破坏正在输入的文本。

**已知取舍**：无多单元格粘贴、无持久化、编辑与清洗步骤不共享撤销栈（清洗是
配置，编辑是数据，两者语义不同）。

## ADR-026：剪贴板粘贴的解析、平铺与裁剪

（2026-10-26）粘贴与复制对称：复制写出 TSV，粘贴读入 TSV，因此"复制一块
到别处"在 RowLens 内部闭环。解析与计划拆成纯函数
（`src/features/grid/paste.ts`），网格只决定起点，父层只提交结果。

四条规则：

1. **解析按 RFC 4180 的引号语义**：引号字段可含制表符、换行和双写引号。
   行尾的单个换行被丢弃——几乎每个来源都以换行结尾，把它当成空行会多粘
   一行空数据；块**内部**的空行保留。
2. **单格选区向外溢出，多格选区被平铺**：与电子表格一致。选中 1 格粘贴
   2×2 块 → 向右下铺开；选中 3×2 粘贴单值 → 六格全填。平铺让"把一列填成
   同一个值"不需要重复粘贴。
3. **越界一律裁剪并计数，不换行续写**：粘贴永不写入用户当前看不见的行。
   裁剪数量通过 `role="status"` 播报（`N row(s) outside the view were not
   pasted`），不静默丢弃。
4. **一次粘贴 = 一条撤销记录**：网格把整块作为 `GridCellEdit[]` 交给
   `commitEdits`，`applyEdits` 一次写入并只压一个批次，因此 Ctrl+Z 一次撤
   整块而不是逐格退。上限检查同样按批次去重计数，超限则整批拒绝并说明。

**焦点即锚点**：粘贴起点取自 `document.activeElement` 对应的单元格，而不是
roving 状态。focus 事件与 paste 可能在同一 tick 到达，此时状态还没重渲染，
用状态会让粘贴落到上一格。

**编辑器内不拦截**：编辑器打开时把 paste 留给 input，否则用户往单元格里粘
一段文本会被当成区域粘贴。

**已知取舍**：不解析 CSV 的逗号分隔（剪贴板约定是 TSV，逗号分隔会把
"1,050" 拆成两格）；无"仅粘贴值/格式"选项；粘贴不扩展行数（没有追加新记
录的语义）。

## ADR-027：编辑持久化到独立的 cellEdits store

（2026-10-26）编辑原先只存在于内存，刷新即丢。要持久化又不破坏"导入行永不
改写"的边界，只有一条路：**另存一份**。IndexedDB 升到 v2，新增
`cellEdits` store（keyPath `datasetId`），每个数据集一条记录：

```json
{ "datasetId": "…", "updatedAt": 1793008098726, "format": 1,
  "cells": [[0, "c0", "edited"], [2, "c1", ""]] }
```

要点：

1. **升级只增不改**：`onupgradeneeded` 里只创建缺失的 store。v1 数据库的
   导入行、导入错误、数据集元数据全部原样保留，编辑 store 初始为空。
2. **扁平元组而不是嵌套对象**：`[[rowIndex, columnId, value], …]` 比嵌套
   Map 更适合结构化克隆与未来的迁移，且**逐条校验**——单个坏元组（负行号、
   非整数、非字符串列 id、类型错误的值）被丢弃，不会让整个数据集的编辑
   全灭。`format` 字段只接受当前版本，其它版本按"没有编辑"处理。
3. **撤销历史不持久化**：刷新是一次新的编辑会话。恢复旧撤销栈等于声称用户
   能撤销他刷新前的动作，而那需要把整条操作链也存下来——代价与收益不成
   比例。UI 上恢复后 Undo 按钮为禁用，`Reset edits` 仍是回到导入值的路径，
   这一点在 E2E 里断言（`toBeDisabled`）。
4. **删除即级联**：`deleteDataset` 在同一个事务里删掉数据集、行、导入错误
   和编辑记录，因此"移除数据集"不会留下孤儿编辑。反过来
   `deleteCellEdits` 只删编辑，不动导入行——两个 store 的独立性有测试覆盖。
5. **重导入会剪枝**：列集合或行数变化的场景由 `pruneEdits` 处理，丢掉指向
   不存在列/行的编辑。返回原对象表示"没有变化"，调用方据此跳过写盘。
6. **写入防抖 400ms**：连续打字不应产生每键一次事务。写失败（配额、私有
   模式）不清空内存覆盖层，只重置持久化标记以便下次重试——持久化是增强，
   不是编辑的前提。

**顺带补上的会话连续性**：只有编辑持久化、没有数据集恢复，刷新后仍然回不
到原数据。所以 `localStorage` 记住最后一个数据集 id（只记 id，不记文件名、
不记任何单元格内容），启动时向 IndexedDB 查询该数据集并重建内存 store。
数据集不存在（被移除、过期、用户清了站点数据）时回退到空状态并清掉指针，
**过期的指针不可能复活已删除的数据**；测试专门覆盖这条路径。

**已知取舍**：编辑仍受 5,000 单元格上限；清洗步骤配置与筛选/排序状态不持久
化（它们是视图配置，不是数据）；同一数据集在两个标签页同时编辑时，后写入
的一方覆盖先写入的一方（无跨标签页协调）。

## ADR-028：启动恢复改为按需分块读取

（2026-10-26）ADR-027 的恢复路径把整份数据读进内存再显示网格：500 行一个
窗口，250k 行就是 500 次 IndexedDB 事务。实测 P1/P2/P3 恢复 1.0s / 2.7s /
6.9s——而网格首屏只渲染 24 行。这是典型的"为不需要的数据付费"。

改为 `LazyDatasetStore`：按 500 行分块，只在真正读取时加载。它保持**同步
`getCell` 接口**，因为网格渲染不能 await：

- 命中已加载分块 → 返回值；
- 未命中 → 返回 `null` 并**在后台发起该分块的读取**，同时 `onChunkLoaded`
  通知视图重渲染，下一帧就是真实值。

正确性依赖两条约束：**分块按需加载的顺序与网格读取顺序一致**（首屏预取
`ensureRows(0, 40)`，滚动时 `warmRows` 预取即将进入窗口的行），因此"未命中"
只会发生在还没上屏的行上。查询、导出、编辑全部直接走 IndexedDB（worker 扫描
与仓储窗口），不依赖这份缓存——它纯粹是渲染层。

**实测**（`e2e/bench/restore.spec.ts`，同机同夹具）：恢复 1,045→282ms、
2,691→394ms、6,931→381ms（3.7× / 6.8× / 18.2×）。恢复耗时不再随数据量
增长，因为只读首屏所需的 500 行分块。

**踩到的坑**：第一版用 `key={chunkRevision}` 让分块到达时重挂载网格，结果
每次加载都把滚动位置重置到顶部——用户恢复后一滚动就被弹回。改为
`dataVersion` 属性：网格在渲染期比较版本并 bump 本地 epoch 重渲染，滚动位置
与焦点都不受影响。E2E 里"恢复后滚到末行仍能看到 T-05000"锁住这条。

**已知取舍**：内存现在随"用户看过多少行"增长，而不是数据集大小；已加载的
分块在会话内不淘汰（受 5,000 行分块粒度约束，浏览全表时仍会读到全部）。
读失败不缓存失败状态，下次读取会重试；失败期间单元格显示空白而不是伪造值。

## ADR-029：分块缓存的 LRU 淘汰与窗口固定

（2026-10-26）ADR-028 的按需分块解决了首屏恢复耗时，但留下一个漏洞：浏览
全表时每个分块都留在内存，250k 行会重新累积到接近全量加载的水平——优化在
"慢慢滚到底"这个最现实的用法下失效。

加入上限 `STORE_MAX_CHUNKS = 40`（20,000 行），按最近使用顺序淘汰。三个
细节决定它是否安全：

1. **Map 的插入顺序即 LRU 顺序**：命中时先 delete 再 set，把该分块移到末尾；
   淘汰从头部开始。`ensureRows` 对已加载的分块也执行 touch，因为"被网格要求
   预热"就是一次使用。
2. **当前渲染窗口固定不淘汰**：`ensureRows(firstRow, lastRow)` 同时更新
   pinned 集合。淘汰跳过 pinned——否则用户正在看的那一屏会被清空，下一帧
   变成空白再异步填回，产生可见闪烁。窗口是"最后一次 ensureRows 的窗口"，
   而不是"所有曾经 ensureRows 过的窗口"：滚动后旧窗口已不在屏幕上，理应
   可淘汰。
3. **窗口大于上限时允许超限**：网格窗口通常 1–2 个分块，远小于 40；若某次
   窗口跨 3 个分块而上限是 2（测试里刻意构造），固定优先于上限——正确性
   （不闪白）优先于内存边界的严格性。

**实测**（`e2e/bench/scroll-memory.spec.ts`，P3 250k 行，跳遍全表）：
滚动后 JS 堆 48 MB，滚动前 337 MB（导入期余量）。没有淘汰时 500 个分块会
持续驻留。

**被淘汰的分块再次读取会重新从 IndexedDB 拉取**，这是设计意图而非缺陷：
缓存是可丢弃的加速层，数据真相始终在 IndexedDB。E2E 用一个 60,000 行
（120 分块，超过 40 上限）的合成文件跳遍全表再回到顶部，断言首行仍是
`R0`，锁住"淘汰后重读"的正确性。

**焦点副作用（实测发现）**：`dataVersion` 变化会重渲染行节点，DOM 焦点因此
掉到 `<body>`。空闲时不可见，但如果用户刚点中一个单元格、分块恰好此时落地，
焦点就被抢走——并行跑 E2E 时表现为 `arrow keys` 用例偶发失败。修复：重渲染
前记录焦点是否在网格内，重渲染后**仅在焦点落到 body 时**恢复到同一单元格，
从不抢回用户主动移走的焦点。

**已知取舍**：上限是固定值而非按内存字节自适应；同屏可见行数极多（例如
超大显示器 + 极高缩放）时窗口本身可能接近上限；没有对"跳来跳去"的访问
模式做预取优化。

## ADR-030：清洗管线作为配置持久化

（2026-10-26）编辑已经跨刷新保留（ADR-027），但清洗管线刷新即清空——用户
重新打开同一份数据要重建步骤。两者不对称，而清洗步骤本来就是纯可序列化
配置（数据契约 §8），存下来没有额外语义负担。IndexedDB 升到 v3，新增
`pipelines` store（每个数据集一条）：

```json
{ "datasetId": "…", "updatedAt": 1793008098726, "format": 1, "steps": [ …CleaningStep ] }
```

**它仍然是配置而不是数据**：保存管线不写任何存储行，应用管线依旧是视图期
投影。"源文件与导入行永不改写"这条边界没有变化，`deletePipeline` 只删配置、
不动行，测试双向断言。

要点：

1. **逐步校验，而不是整份接受或整份丢弃**：记录可能比 schema 活得久（重
   导入会改列，旧版本可能写入本版本不认识的步骤类型）。`pruneStep` 逐条
   验证类型、id、scope；一条坏步骤只损失它自己。
2. **列清单失效时整步丢弃**：显式列清单里的列全都不存在时，若退化成"所有
   列"会**静默改变步骤语义**——那比丢掉这一步更糟。部分失效则只保留仍存在
   的列，因为范围缩小是可解释的。
3. **拒绝重复 step id**：面板以 id 作为 key，两个步骤共用一个 id 会互相编辑。
4. **未知 format 按"没有管线"处理**：与编辑记录同一策略，宁可空管线也不
   猜测旧格式。
5. **重置即删除记录**：空管线写入时删掉记录，而不是存一个空数组——"重置"
   应该在存储层也真的是重置。

**恢复时的顺序**：先取数据集元数据与编辑记录，再取管线，然后一次性
`setView`，避免"先显示未清洗视图、再闪一下变成清洗后视图"。通知文案把两项
合并成一句（`Restored your previous session with 1 cell edit and 1 cleaning step.`）。

**已知取舍**：筛选/排序/隐藏列当时不持久化（见 ADR-031，后来改为持久化）；
管线没有版本历史或多套预设；跨标签页同时编辑同一数据集仍是后写覆盖。

## ADR-031：查询视图（搜索/筛选/排序/隐藏列）作为配置持久化

（2026-10-26）ADR-030 把"筛选/排序/隐藏列不持久化"写成了取舍，理由是它们
描述"此刻在看什么"，随会话重置更符合预期。实际使用后这个理由站不住：
重开同一份数据，用户第一件事往往是重新输入刚才的筛选条件，而清洗管线和
编辑都已经保留下来了——三者不对称。视图同样是纯可序列化配置，存下来没有
新的语义负担。IndexedDB 升到 v4，新增 `views` store（每个数据集一条）：

```json
{ "datasetId": "…", "updatedAt": 1793008098726, "format": 1,
  "search": "north", "columnFilters": { "c0": "T-0" },
  "sort": { "columnId": "c1", "direction": "asc" }, "hiddenColumns": ["c2"] }
```

**它仍然是配置而不是数据**：保存视图不写任何存储行，恢复视图只是把同一条
查询再跑一遍。"源文件与导入行永不改写"这条边界没有变化。

要点：

1. **排序按列 id 存，不按位置存**：记录属于某个数据集，但 id 在"重导入后
   列顺序变化"时仍然指向同一列，位置则不会。主线程在读写两侧做 id ↔ 数据集
   下标映射。
2. **逐字段校验**：记录可能比 schema 活得久。失效的筛选列、失效的排序列、
   失效的隐藏列各自被丢弃，只损失那一项；搜索词超长（>2000 字符）视为损坏
   记录，宁可回到空视图也不重跑一次荒谬的扫描。
3. **"隐藏所有列"不恢复**：那会留下一个没有网格可操作的死局，比丢弃这条
   设置更糟，所以按"未隐藏任何列"恢复。
4. **筛选键走白名单**：只写入确实存在的列 id，`__proto__` 之类的构造键被丢弃
   而不是赋值。
5. **空视图删除记录**：`isActiveView` 为假时删除记录而不是存空对象——Reset
   在存储层也真的是重置。Reset 现在同时清空隐藏列，状态行也会显示
   `N columns hidden`，否则"只有隐藏列"的视图会让 Reset 凭空出现。
6. **防抖依赖视图签名，而不是整个 view 对象**：每次查询结果都会产生新的 view
   对象（行索引、忙碌标志），依赖它会让 400 ms 防抖被反复重置，慢查询能无限
   推迟写入。三条持久化效应（编辑/管线/视图）统一改为依赖派生签名。

**恢复顺序**：元数据 → 编辑 → 管线 → 视图，然后一次性 `setView`，所以首屏
就是"已筛选、已排序、已清洗"的样子，不会先闪一下全表。通知把各项合并
（`Restored your previous session with 1 cell edit and its filters and sort.`）。

**已知取舍**：视图只有一份，没有多标签视图；滚动位置不恢复（它
依赖渲染窗口尺寸，恢复出来往往和用户记忆不符）；跨标签页仍是后写覆盖。

## ADR-032：清洗预设按表头名匹配，且独立于数据集

（2026-10-26）ADR-030 让管线跟着数据集走，ADR-031 让视图跟着会话走，但
两者都是"这一份数据"的状态。实际使用里反复出现的需求是：同一套清洗规则
（去空白 → 按 Ticket 去重 → 只留 4 列）每周用在不同导出的文件上。管线
持久化解决不了这个——换个数据集就是一条空管线。

因此新增**命名预设**：把当前管线存成一条可复用配方，可应用到任何数据集。
IndexedDB 升到 v5，新增 `presets` store。

**关键决策：预设按表头名（label）引用列，不按列 id。** 列 id 是位置性的
（`c0`、`c1`……），同一个 `c1` 在 A 文件是 Status、在 B 文件可能是 Note。
若存 id，跨文件应用会**静默改错列**——这是最糟的一类错误，因为结果看起来
完全正常。E2E 用一对"表头相同、列序不同"的夹具专门守这条：源文件里
Status 是第 2 列，目标文件里是第 3 列，预设必须仍然只 trim Status。

由此产生的三个处理原则：

1. **重复表头不猜。** 数据集允许同名列共存（按设计是独立列）。一个匹配到
   多列的标签无法唯一确定目标，因此**丢弃**而不是取第一个。捕获时丢弃会让
   整步无法忠实表达（该步被略过并计数）；应用时丢弃会让该标签被略过并计数。
2. **范围不会退化成"所有列"。** 与 ADR-030 一致：显式列清单全部失效时丢掉
   这一步，而不是悄悄扩大范围。
3. **结果一律播报，不静默。** 保存时报告"因表头重名略过 N 步"，应用时报告
   "略过 N 步 / N 个列名无法唯一匹配"；一步都没应用上时明确说"无法应用"，
   而不是留一个看起来生效的空管线。

**预设不是数据集数据。** `deleteDataset` 的级联删除**不包含** `presets`：
删掉来源数据集后配方必须还在，否则"用在另一个文件上"这个唯一价值就没了。
仓储测试双向断言这一点。预设保存在一条全局记录里（keyPath `id`，固定键
`all`），因为它是手工维护的小列表，"保存/重命名/删除"一次原子写入比逐条
更新更简单。上限 50 条，名字上限 60 字符，重名保存需要二次确认（第二次
点击按钮变为 Replace），不静默覆盖别人的配方。

**校验**：与管线/视图同一策略——逐条验证步骤类型、scope、标签列表；未知
类型只损失该步；**没有任何可用步骤的预设整条丢弃**（应用它等于什么都不做，
提供这样一个按钮是在骗人）；重复 id 丢弃后者。

**已知取舍**：没有预设导入/导出（跨浏览器迁移需要手工重建）；预设不含
视图与筛选；应用预设是**替换**当前管线而不是追加。

**顺带修复**：`e2e/support.ts` 的 `resetSession` 原先在 `onblocked` 上就
resolve，留下一个挂起的删除请求。应用启动即打开 IndexedDB 读预设后，这个
挂起请求会在不可预测的时刻真正执行，把**下一个**测试正在播种的数据库拆掉。
当时的修正（先导航到 `about:blank` 再删除）是**错的**，见 ADR-033 末尾。

## ADR-033：预设文件导出/导入——配方可以离开浏览器

（2026-10-26）ADR-032 之后，预设只能活在这一个浏览器里。换机器、重装、
换浏览器，配方就得从零重建——而"配方"这个词的全部意义就在于可复用。新增
**预设文件**：JSON 文档，从清洗面板导出、再导入。

```json
{ "format": 1, "exportedAt": "2026-10-26T12:00:00.000Z", "presets": [ …CleaningPreset ] }
```

**隐私边界**：文件里只有配置——步骤类型、启用标志、列**表头名**。没有单元格
值、没有行数、没有文件名。表头名是唯一可能敏感的内容，而它们离开设备只因为
用户点了"Export presets"。这一点写进了 README 和面板提示。

**导入是不可信输入**：文件字节上限 1 MiB（误选二进制不进内存解析）、防御性
解析、每条预设走与 IndexedDB 相同的 `prunePreset` 校验。坏条目只损失自己。
错误文案不回显文件内容——列名可能就是用户不想在错误横幅里看到的东西。

**导入永不覆盖现有配方**：覆盖无法撤销。重名条目被跳过并计数，用户改完名可
以重试。id 碰撞（不同名同 id 的手工编辑文件）给新 id 而不是丢弃，因为面板按
id 作 key。合并结果一次播报：导入 N 条 / 重名跳过 N 条 / 超上限跳过 N 条 /
文件中 N 条无法读取。

**导出用下载保存器而不是流式选择器**：预设文件只有几 KB，不需要 File System
Access 的真流式；这样也避免把 CSV 专用的建议文件名逻辑搬进预设路径。为此给
下载保存器加了可选 MIME 类型（默认仍是 CSV），顺手修了一个真陷阱：原实现在
**只要传了 hooks 就不触发下载点击**，一个只想改 MIME 类型的调用方会静默
拿到一个永远不下载的保存器——已改为只在实际提供了 `onStartDownload` 时才
抑制点击，并加了回归测试。

**已知取舍**：文件不加密（列名明文）；无跨文件去重（同名即跳过）；上限仍
是 50 条。

**测试基建的修正（ADR-032 里的错误修正）**：上一条 ADR 说"导航到
`about:blank` 关掉连接再删除"。实测发现 `about:blank` 是不透明源（opaque
origin），它看到的 `indexedDB.databases()` 是空的——那个"修正"让
`resetSession` 变成了**静默 no-op**，预设从那个批次起就没被真正清理过。现有
用例仍然通过，是因为多数用例靠 `loadSample` 的容忍语义掩盖了脏状态。现在改用
CDP `Storage.clearDataForOrigin`：它作用于真实源、无视连接占用，然后重载。
E2E 的"导出→干净会话导入"用例守这条。

## ADR-034：搜索框的 `列名:值` 定向语法，其余一切保持字面

（2026-10-26）全局子串搜索在多列大文件上噪声很大：搜 `open` 会同时命中
Status、Note 和任何含这个词的列。列筛选（Filter 弹层）能定向，但要打开弹层、
逐列填输入框——离键盘最近的那条路径反而最绕。在搜索框里支持
`Status:open` 是补齐这个缺口的最低成本方式。

**语法只有这一条**：空白分隔 term，term 之间 AND；`列名:值` 把该 term 限定
到那一列（表头精确匹配、大小写不敏感）；含空格的表头用双引号
（`"First response (h)":14`）。数据契约 §4 同步更新；正则/通配符仍然被
明确排除。

四条防意外规则，全部源于"宁可少做事也不猜"：

1. **前缀不是任何表头时，整个 term 仍是普通子串（冒号含在内）**。`http://…`、
   `12:30`、拼错的表头（`Stat:open`）都不受影响。若把拼错的前缀静默降级为
   "全局搜索 open"，用户会以为自己在定向搜索——这比搜不到更糟。
2. **引号只在表头位置有意义**。`open"foo bar"` 里的引号按字面搜索：想要搜
   真实引号字符的用户仍然能搜到。只在 term 以 `"` 开头且有闭合引号加冒号时
   才解析为表头引用。
3. **重复表头搜索所有同名列**。数据集允许同名列共存；挑第一个会静默藏起
   一半的匹配。这与 ADR-032 预设的处理不同（预设丢弃歧义标签，因为它的
   语义是"改这一列"），搜索的语义是"在这些列里找"，多列并入是正确外延。
4. **`列名:`（空值）等价"不过滤"，与列筛选的空值规则一致**，并且在解析层
   丢弃——空 term 会把引擎拖进一次全表扫描却什么都不排除。

**协议与实现**：`QueryRequestSpec.search: string` 改为
`searchTerms: SearchTerm[]`，解析在主线程完成（那里才有列名），worker 只见
解析后的列下标。引擎只有一个实现（worker 与无 Worker 回退共用），一个 term
匹配其任一列、所有 term 都须命中。副作用是性能更好：定向 term 只折叠自己
那一列的值（有引擎测试锁定折叠器只被调用于目标列），全局 term 行为与从前
完全一致，折叠缓存（ADR-022）不受影响。

**已知取舍**：不做短语搜索（引号包查询文本没有特殊含义）；不自动补全表头；
`列名:` 静默无效果（状态行会显示全量计数，用户能看出来）。


## ADR-035：数值排序 = 显式开关 + 严格解析 + 分区不换位

（2026-10-27）排序一直是纯 UTF-16 字符串序：`9` 排在 `1,050` 后面（"9" > "1"），
`00123` 排在 `42` 前面。数据契约 §4 从第一版就写明：默认字符串序，类型选择
交给用户，**不做推断**。这个批次兑现了后半句。

**为什么不推断**：一列 999 个数字混进一个 `"N/A"`，自动推断会让整列从数值序
悄悄掉回字符串序——数据没变、操作没变、结果变了，这正是本项目一贯拒绝的
"静默改语义"。所以数值模式是一个显式开关：排序列的表头上出现 `123` 按钮
（`aria-pressed`），点一下按数字重排，再点一下回到字符串序；方向循环键保留
原方向。开关只在排序列上出现——没有排序就没有数值序可言。

**解析规则固定，宁严勿宽**（`parseSortableNumber`）：

- 接受：去首尾空白后的十进制（可选正负号、小数点、指数 `1e3`）。
- 接受：严格 en-US 千位分组 `1,050`——首组 1–3 位、后续组**恰好三位**。
  `1,05` 被拒绝而不是当成 105；猜测德式 `1.050` 更是明确不做。
- 拒绝：`0x1a`、`Infinity`、`NaN`、`$4`、`N/A`、空串。`Number()` 本身太宽容
  （十六进制、Infinity 都能过），所以用白名单正则而不是直接转。

**混合列的顺序规则**：分区为 数字 → 非数字文本 → 空单元格；分区顺序在升序
和降序下**完全相同**，只有分区内比较随方向反转。这与既有的"缺失值双向都
在最后"是同一条原则的延伸：方向改变的是"怎么比"，不是"谁算数"。分区内的
同值保持原始顺序（稳定排序，键是原始行序）。

**实现落点**：`sort` 全链路（GridSort → 视图 → 协议 → 引擎）都带 `numeric`
布尔位；引擎仍在扫描期抓原始字符串键，排序时才按模式选择比较器，所以清洗
（trim）和编辑都自然参与数值排序——trim 后的 `" 12 "` 变 `"12"` 就能被解析。
排序键不含数值时行为与从前逐字节一致。

**两个顺手修掉的既有缺陷**：

1. **表头 CSS 从上线第一天起全部失效**：样式写的是 `.grid-table th`，而网格
   自诞生就是 `div[role='columnheader']`——8 条规则（表头背景、粘性、边框、
   箭头显隐）从未命中任何元素。用计算样式探针证实（背景透明、不粘性、无边
   框）后改为按 role 选择。箭头显隐规则生效后，箭头从"永远可见"回到设计的
   "悬停/聚焦/已排序时可见"。
2. **查询依赖键漏了 numeric**：`sortKey` 只含 `列:方向`，点开关不触发重查，
   界面毫无反应。jsdom 探针抓到（切换后窗口值不变）后把 numeric 并入键。
   两个缺陷都是新功能的探针顺手暴露的——不是本批引入的回归。

**已知取舍**：不解析日期（ISO-8601 文本字符串序本来就对；非 ISO 日期格式
解析是locales 泥潭）；不解析币种符号；编辑把数字改坏会落到文本分区（可
预期，不报错）。

## ADR-036：导出所选区域——Copy 的流式对应物

（2026-10-27）选区一直只能复制为 TSV，且有 10 万格上限；超限提示让用户
"改用 Export CSV"，但 Export CSV 的范围只有 Filtered/All 两种，表达不了
一个矩形——这是产品里一条自相矛盾的半开回路。本批把它闭上：Export 对话框
新增第三种范围 **Selected range**（N rows × M columns）。

**语义 = "屏幕上这个矩形，原样"**：

- **行**：当前视图顺序（视图行本就是清洗后的集合），不是数据集行号序。
- **列**：网格列序（可见列 ∩ select-columns 幸存列）。
- **值**：与网格显示一致（编辑覆盖 + trim），也就是与 Copy 相同的读法。
- 行生成器与 Filtered/All 完全共用——选区行已是清洗后集合，对它们再跑一遍
  幂等管线（trim²=trim、对已去重集合再去重=不变），行为与 Filtered 路径
  一致，无特殊分支语义。

**快照而非活映射**：打开对话框时把选区映射成数据集行索引 + 列下标并存起来。
对话框是模态的，但查询可能在打开瞬间仍在跑——一个迟到的查询结果若改变
`rowIndices`，活映射会静默改变导出内容。快照让"确认导出的是什么"在打开那
一刻就定死。快照只在对话框打开期间存活，关闭即清空。

**单格不提供该范围**：选区永远存在（焦点格就是 1×1），但导出一个格子不是
"范围导出"——那是单元格 Copy 按钮的事。只有 ≥2 格时对话框才出现 Selected
range 选项，且它成为默认选中项——用户选了一片再点 Export，意图是明确的。

**无格数上限**：Copy 的 10 万格上限源于把整个 TSV 拼进内存；导出走流式
序列化，逐行写。超限提示改为指向"Export 对话框的 Selected-range 范围"，
这句话终于字面为真。

**已知取舍**：选区是视图坐标，查询变化会移动所指的行（快照只保证对话框
打开期间不变，不保证"重开对话框还是同一片"）；跨行选择经行表头选整行时
导出该行全部可见列，与显示一致；Raw 模式对选区导出同样可用（含公式注入
风险提示）。

## ADR-037：导出与估算读"总行源"，与渲染缓存分离

（2026-10-27）发布前的全量代码评审（双线：安全/质量线 + 架构线）发现两个 HIGH，
根因是同一个架构缝隙：`CellSource { getCell }` 这一个抽象被两种缺失语义的存储
共用——内存库的 `null` = 这个格子是空的，懒加载恢复库的 `null` = 这个块还没到货。
网格能容忍歧义（空白一帧、异步补齐、重渲染）；导出不能。恢复会话导出 All rows
时，预取窗口之外的每个块都同步读到 null，写进文件的就是空单元格——行数正确、
内容为空，主输出产物静默损坏。ADR-028 写明"导出……不依赖这份缓存"，实现漂移了，
`string | null` 返回类型对混淆毫无提示。

**决策**：`ReadyData` 增加可选的 `readStoredRows(offset, limit)` 总行源（恢复路径
提供，直连 `repository.readRows`）；导出行生成器分两条路——内存数据集维持逐格直读
（永不 miss），恢复数据集按视图顺序分批（500 行/批）经 `readRowsByIndices` 走
IndexedDB 键区间窗口，把连续行号并成尽量少的读、编辑覆盖叠加其上、清洗变换照旧。
公式风险估算同根同修：改为异步按范围计算 + 缓存（首次返回 null = "counting…"，
落地后对话框经依赖身份变化重新询问），渲染缓存不再参与任何产出物。

**排序后的导出顺序是碎片化的**（视图顺序≠存储顺序），相邻批次的行可能落在不同
块——`readRowsForIndices` 按连续游程分组读，最坏情况每次游程一行；正确性优先，
不为一类排序优化而引入内存换序。内存有界：每批至多 500 行进 Map。

**顺带固定的配套**：`CellSource` 的注释与 `lazy-store.ts` 的头注释改为如实描述
"谁允许 miss"；导出对话框的风险估算 effect 依赖改为计数器身份而非整个 props
（打开对话框期间的每次父渲染不再重启全格扫描）；查询 worker 的单槽门改为
"在跑则排队、只保留最新、取消可撤队"，客户端 CANCEL+START 背靠背的超步路径
有了 worker 行为级回归测试（旧代码下新查询被静默丢弃、busy 永久卡死）。

**已知取舍**：碎片化顺序的导出在极端排序下读放大（每次游程一个键区间）；内存
数据集与恢复数据集走两条生成路径（共享变换与序列化，分支只在行来源一行上）。
