# RowLens 性能实测结果

数据来源：`e2e/performance.spec.ts`（`PERF=1` 门控）+ `e2e/bench/generate.ts`
确定性合成数据。**每个数字都来自一次真实运行**；未测的项目明确标注。

## 测试环境

| 项 | 值 |
|---|---|
| 日期 | 2026-10-26 |
| 浏览器 | Microsoft Edge 156.0.8078.4（Chromium，headless） |
| 设备 | Windows 11，8 逻辑核心，16 GB RAM（`navigator.deviceMemory`） |
| 产物 | 生产构建（`vite build`），Vite preview 服务 |

## 基准配置与结果

| 配置 | 文件 | 行×列 | 导入(ms) | 搜索(ms) | 排序(ms) | 导出(ms) | JS 堆(前→后) |
|---|---|---|---|---|---|---|---|
| P1 | 11.2 MiB | 20,000×20 | 2,201 | 2,654 | 455 | 495 | 3→50 MB |
| P2 | 54.1 MiB | 100,000×30 | 8,751 | 17,430 | 2,083 | 2,596 | 3→315 MB |
| P3 | 95.6 MiB | 250,000×40 | 32,058 | 64,659 | 5,016 | 5,331 | 3→618 MB |

测量定义：

- **导入**：`setInputFiles` 到状态行显示 `N of N rows match`（含 worker 解析、
  分批持久化、首个查询完成）。
- **搜索**：输入 `PERFNEEDLE`（约 0.5% 行命中）到状态行计数离开全量值
  （含 250ms 防抖）。
- **排序**：点击 `col_1` 表头到 `aria-sort=ascending` 且 busy 标记消失。
- **导出**：对话框确认到下载事件（下载回退路径，150 MiB 上限内）。
- **JS 堆**：`performance.memory.usedJSHeapSize`，导入前 → 导出后。

## 观察与结论

1. **导入随文件大小近线性**（11.2→95.6 MiB，2.2→32.1s），期间 UI 保持可操作
   （进度+取消可用；主线程仅做 IndexedDB 批次写入）。未在基准中断言主线程
   长任务占比——列为未测项。
2. **搜索是当前最大瓶颈**：P3 全表字面搜索 64.7s。逐单元格
   `toLocaleLowerCase + includes`（250k×40 ≈ 1000 万次）主导耗时；排序趟
   同样扫描全表但无逐格工作，仅 5.0s，佐证瓶颈在搜索的字格处理而非扫描
   本身。缓解方向（未实施）：预计算小写化列缓存 / worker 内分块大小写折叠
   复用 / 限制搜索列范围。
3. **排序趟 = 全表扫描 + 单键排序**：P3 5.0s，其中扫描占绝对多数；排序键
   仅取自单列。
4. **导出**：流式序列化 + 下载回退，P3（250k 行）5.3s，内存峰值来自写穿
   缓存与结果数组。
5. **内存**：P3 后 JS 堆 618 MB（约 6.5× 文件体积），来自写穿缓存 + IDB
   结构 + 索引数组，受 100 MiB 导入上限约束、有界；低内存设备上是风险项。
   未做峰值内存的细粒度剖析——列为未测项。
6. **无谓词全量视图走快路径**（本轮新增）：不加搜索/筛选/排序/清洗时的
   初始视图直接由 finalize 行数生成索引，不再触发扫描，也因此不会被
   200,000 匹配上限拦截（该上限只约束带谓词的查询结果）。

## 缓存优化复测（2026-10-26 追加）

查询 worker 增加小写化值缓存（ADR-022：按数据集缓存折叠值，重导入失效）。
同一方法学、同机复测：

| 配置 | 首次搜索(ms) | 复测前(ms) | 重复搜索(ms，专项) |
|---|---|---|---|
| P1 | 1,666 | 2,654 | — |
| P2 | 9,729 | 17,430 | **2,638**（12,366 首趟 → 2,638 复用，4.7×） |
| P3 | 34,781 | 64,659 | — |

专项对比用例：`e2e/bench/search-cache.spec.ts`（PERF=1，P2 连续两次相同
搜索，断言结果一致）。导入/排序/导出数值与首测一致（波动属正常噪声）。

## 启动恢复优化复测（2026-10-26 追加）

编辑持久化后，刷新会重建内存 store。首次实现按 500 行窗口逐次读取整份数据
（250k 行 = 500 次事务），实测：

| 配置 | 行×列 | 恢复(ms，逐窗全量) | 恢复(ms，按需分块) | 提速 |
|---|---|---|---|---|
| P1 | 20,000×20 | 1,045 | **282** | 3.7× |
| P2 | 100,000×30 | 2,691 | **394** | 6.8× |
| P3 | 250,000×40 | 6,931 | **381** | 18.2× |

方法：`e2e/bench/restore.spec.ts`（PERF=1）。导入 → 等待会话写入落盘 →
`page.reload()` → 等到状态行显示全量计数且首个单元格可见，用 epoch 时间计
（`performance.now()` 在重载后归零，不可用于跨文档计时）。同一份 `.bench`
夹具、同机、同浏览器。

**结论**：恢复耗时不再随数据量增长（282/394/381 ms），因为只读网格实际需要
的 500 行分块。优化前 P3 的 6.9s 里绝大部分是它永远不会渲染的 249,500 行。
数据量越大收益越大，这正是分块懒加载与"先读全部"的本质差别。

## 分块淘汰后的滚动内存（2026-10-26 追加）

按需分块解决了首屏恢复耗时，但浏览全表会把每个分块都留在内存，等于退回
"全量加载"。加入 LRU 上限（40 个分块 = 20,000 行，当前渲染窗口固定不淘汰）
后实测：

| 配置 | 跳转步数 | 滚动耗时 | 滚动前 JS 堆 | 滚动后 JS 堆 |
|---|---|---|---|---|
| P3（250,000×40） | 25（每步 10,000 行，覆盖全表） | 8,859ms | 337 MB | **48 MB** |

方法：`e2e/bench/scroll-memory.spec.ts`（PERF=1）。导入 → 刷新（走懒加载
路径）→ 记录堆 → 以 10,000 行为步长跳遍全表（每步等 120ms 让分块落地）→
记录堆。堆值来自 `performance.memory.usedJSHeapSize`。

**结论**：滚动前 337 MB 是导入期写穿缓存尚未回收的余量；滚动全表后降到
48 MB，说明已加载分块被正确淘汰、没有被滚动过程累积。若没有淘汰，P3 全表
约 500 个分块会持续驻留。

## 与验收目标对照（测试文档 §4）

- P2 不出现 UI 长时间冻结、任务可取消：导入/查询均在 worker；查询自动
  supersede（旧查询不再占据结果），但**长查询无显式取消按钮**（下一批
  候选）——冻结未用指标断言，标为未测项。
- 内存不无界增长：受文件上限约束（见观察 5）。

## 未测项（明确列出）

- 主线程长任务（long-task）占比与导入期间交互延迟。
- 峰值内存细粒度剖析（按缓存/索引/字符串分解）。
- Firefox / Safari 矩阵（无环境，见 README 已知限制）。
- 超过 100 MiB 的行为（按设计直接拒绝，属功能测试覆盖而非性能）。

## 复现

```bash
npm run build
PERF=1 npx playwright test e2e/performance.spec.ts   # 导入/查询/排序/导出
PERF=1 npx playwright test e2e/bench/restore.spec.ts # 启动恢复
PERF=1 npx playwright test e2e/bench/search-cache.spec.ts  # 搜索缓存专项
PERF=1 npx playwright test e2e/bench/scroll-memory.spec.ts  # 滚动内存
# 结果输出至 test-results/bench/results.json 与控制台表格
```
