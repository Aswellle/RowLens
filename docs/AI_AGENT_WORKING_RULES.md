# AI Agent 工作协议与质量门槛

## 1. 目标

让 AI 编程代理以最小返工风险交付可靠的软件，而不是生成大量难以维护的代码。以下规则适用于本资料包内所有项目。

## 2. 工作前置检查（强制）

每次开始编码前：

1. `pwd` / `Get-Location`，确认当前仓库和目标目录。
2. 检查 `git status --short --branch`，确认分支、未提交修改和未跟踪文件；禁止覆盖用户未提交内容。
3. 阅读现有 README、项目清单、包管理文件、构建脚本、CI、测试、许可证与目录结构。
4. 运行已有的快速测试/类型检查/构建，记录基线结果。已有失败必须区分“历史失败”与“本次引入失败”。
5. 对照对应项目的 PRD、架构和验收标准，列出预计文件改动、数据流、风险和验证命令。
6. 发现仓库并非空白时，不得假设可以从零覆盖脚手架；沿用合理现有约定，只有在证据充分时才改动。

## 3. 阶段执行协议

- 一次只执行一个阶段；阶段交付必须包含代码、测试、验证结果与剩余问题。
- 每个阶段开始前给出 5–10 行以内的实施摘要；完成后报告改动文件、运行命令、实际结果和未覆盖风险。
- 除非测试、配置或接口需要，不要顺手重命名或改写无关文件。
- 不得只创建空壳、占位 TODO 或伪实现后声称完成。
- 不得把“构建成功”表述成“功能完全验证”。端到端行为必须有对应证据。
- 不允许跳过测试来赶进度。若某项无法测试，必须写明阻碍和手动验证步骤。
- 不可虚构命令输出、性能数字、浏览器兼容性或测试覆盖率。
- 依赖需先证明必要性；避免引入 UI 大套件、服务器、数据库服务、Docker 或大型 WASM 运行时，除非需求/ADR 明确允许。
- 更新依赖时，保留 lockfile 同步更新，不使用浮动版本伪装可复现性。

## 4. 安全与数据保护

- 用户数据默认视为敏感数据。最小化收集，最少复制，不写入日志/遥测。
- 不将数据、密钥、令牌、个人文件名或原始记录发送给外部服务。
- 外部输入必须被视为不可信；禁止把单元格/文件名/Markdown 内容直接作为 HTML 注入。
- 文件操作默认非破坏性；不覆盖源文件、不自动删除用户文件、不执行用户数据内容。
- 错误消息不应泄露完整敏感内容；仅给出必要行号、字段或错误类别。
- 修改许可证、隐私承诺、安全边界或导出语义必须显式记录。

## 5. 工程规范

- TypeScript 启用 strict 检查；不要用 `any` 绕开模型。必要时用明确的 `unknown` 和解析函数。
- 数据解析、清洗规则与 UI 分离；规则应尽可能是纯函数，便于单元测试。
- 错误使用可区分的类型或错误码；UI 根据错误类别显示可行动说明。
- 异步任务具备取消、进度、失败清理与竞态控制。
- 对用户可见交互考虑键盘、焦点、屏幕阅读器、窄视口和 reduced-motion 设置。
- 所有文件路径均通过安全解析；不能为了方便把用户给出的路径拼进 shell 命令。
- 不添加未使用的依赖、死代码、无必要抽象或重复状态来源。

## 6. 最低验证门槛

按项目选择适用命令，最低包括：

- 依赖安装可复现；
- lint（若仓库配置了 lint）；
- TypeScript 类型检查 / Python 静态语法检查；
- 单元测试；
- 生产构建；
- 关键流程端到端或手动验收；
- 对安全敏感路径做负向测试。

最终报告至少包含：

1. 已完成范围；
2. 修改/新增文件；
3. 实际运行的命令与通过/失败结果；
4. 关键功能的测试证据；
5. 尚存缺陷、风险与未验证项；
6. 是否达到当前阶段验收条件。

## 7. 需要暂停并向用户报告的情况

只有遇到这些阻塞才询问用户：破坏性操作、需要真实密钥/账户、许可证/品牌决策重大冲突、无法从上下文安全推断的数据丢失语义，或需求之间不可调和的矛盾。其他情况优先采用文档中的默认决策并继续。
